# identuum-ui v0.2.2 — release notes

Tag: `v0.2.2` on `main`. Published with the manual `publish-image.yml`
workflow (`version_tag: v0.2.2`, `latest_tag: false`; the workflow also
pushes a `sha-<short>` tag), under the owner's grant for this release.

## Why this release

The identuum-idp-oss `v0.5.0` install pins the UI by digest. Against OSS,
`v0.2.1` shows two org-admin pages wrong; this release fixes both and
changes nothing else.

- **Applications: the created client** (`3494727`) — OSS answers a create
  with `{"client": {...}, "client_secret": "..."}`. The success panel read
  the fields from the top level and showed " has been created." with an
  empty client ID and no redirect URIs. The nested client is read now, the
  one-time secret from the top level; a flat answer still works.
  Test: `src/__tests__/create-application-response.test.ts` — red on
  `v0.2.1`'s code (`expected { id: '', client_id: '', …(9) } to match object
  { …(5) }`), green with the fix.
- **Users: account status** (`c9ede3c`) — OSS carries `banned`, not
  `active`, on a user, and writes `banned = !active`. The users list and the
  user detail coerced the absent `active` to false, so every user, the
  signed-in admin included, showed as Disabled and offered only "Enable".
  `active` is derived as `!banned` when absent; an explicit `active` still
  wins. Test: `src/__tests__/user-active-from-banned.test.ts` — red on
  `v0.2.1`'s code (`expected [ false, false ] to deeply equal [ true, false ]`),
  green with the fix.

Both fixes were found by the Plan D browser run against the OSS binary and
cherry-picked from branch `ui-in-binary` (`770982c`, `b7dd4dd`) with their
provenance lines.
