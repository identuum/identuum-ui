# identuum-ui v0.2.3 — release notes

Tag: `v0.2.3` on `main`. Published with the manual `publish-image.yml`
workflow (`version_tag: v0.2.3`, `latest_tag: false`; the workflow also
pushes a `sha-<short>` tag), under the owner's grant for this release.

## Why this release

The identuum-idp-oss `v0.5.0` release-candidate rehearsal found three
blockers in `v0.2.2`. This release fixes all three and changes nothing else.

- **CSRF: the IdP proxy and sign-out refuse other origins** (`355a22c`) —
  the `/api/idp` proxy lifts the browser's `access_token` cookie into a
  Bearer and strips Origin/Referer, and nothing checked where a
  state-changing request came from. `SameSite=Lax` stops cross-site pages
  but not a page on another origin of the same site: the rehearsal created
  a role in the victim's organization from `http://localhost:<other port>`.
  One guard now runs on every method other than GET/HEAD/OPTIONS on the
  proxy and on `POST /api/auth/logout` (the only state-changing
  `/api/auth/*` route). It allows a request only when Origin equals the
  runtime config's `ui_origin` (when that is unset, the Origin host must
  equal Host), or, with no Origin, when `Sec-Fetch-Site: same-origin`.
  Anything else gets `403 {"error":"cross_origin_refused"}` before any
  upstream call, and one WARN line naming the method, path and reason.
  Test: `src/__tests__/same-origin-guard.test.ts` — red on `v0.2.2`'s code
  (8 of 15 failed: cross-site, same-site other port, missing Origin and
  Sec-Fetch-Site, and logout from another origin were all forwarded), green
  with the fix.
- **Sign-out lands on /login** (`7405e33`) — the logout route built its
  Location from `req.nextUrl.origin`, which inside the container is the
  listen address `http://0.0.0.0:7104`; every sign-out on the documented
  compose ended on a connection error. The 303 now carries a relative
  Location. Test: `src/__tests__/logout-redirect.test.ts` — red on
  `v0.2.2`'s code (`expected 'http://0.0.0.0:7104/login' not to contain
  '0.0.0.0'`), green with the fix.
- **Users: a disabled member is Disabled, with Enable** (`80c0035`) — OSS
  stores an admin-disabled org_user and a self-registrant held for approval
  the same way (`banned=true`), and the list and detail page called every
  banned org_user "Pending approval" with no Enable control. The status now
  reads the organization's registration policy: a banned org_user is
  Disabled with Enable unless the organization takes public registrations
  and holds them for approval (or its policy could not be read); there it
  is labelled "Disabled or awaiting approval" and the detail page offers
  both Enable and Approve registration. Test:
  `src/__tests__/org-admin-disabled-vs-pending.test.ts` — red on `v0.2.2`'s
  code (8 of 12 failed), green with the fix.

All three were proven live against a locally built image in a scratch
stack with the `v0.5.0-rc` OSS image: the rehearsal's cross-origin probes
answer 403 and create nothing while the same-origin request still works; a
Next server action (Disable) replayed from another origin is refused by
Next's own origin check (`Invalid Server Actions request`) and the member
stays enabled, while the same replay from the UI origin works; sign-out
lands on `/login`; Disable → Enable works from the Users page.

## Operator notes

- The CSRF guard compares Origin with `ui_origin` from the UI runtime
  config. Set `ui_origin` to the exact origin browsers use for the UI
  (scheme, host and port); a browser on any other origin — another
  hostname or IP for the same server included — is refused on every
  state-changing request.
- After publication, the identuum-idp-oss compose's UI line should be
  re-pointed to the published `v0.2.3` index digest — a post-publish step in
  that repository.
